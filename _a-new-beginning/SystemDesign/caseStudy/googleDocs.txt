The challenge of real time collaborative editing arises from communication delays.
Had it been instantaneous, it would be as simple as a single user editing tool as update from
the peer would appear as if it is done by the current user.
A users expectation is that his edits to be incorporated immediately.
You must apply remote edits that refer to document positions that no longer exist — because your own edits have shifted or
destroyed those positions — and you must still end up with the same final document state on all devices.

Request payload contents:
When a participant makes an update, or receives an update from others, what should the request payload contain?
Payload contains only changes (the delta): Sending and receiving just the updates made with revision number so that we know to which 
version the changes to applied upon.
A short response time (under 500ms) is required for a real-time WYSIWIS (What-You-See-Is-What-I-See) experience otherwise the changes
would get applied on an outdated version destryoing the integrity of the document.

Network architecture / communication model:
Client-server model: Central server; all participants communicate only with the server
Peer-to-peer: No central server; all participants act as both a server and client

In a client-server network model, participants (clients) request resources from a central server and send payloads to it. 
The server processes these requests and provides the appropriate responses.

Advantages:
Centralized source of truth: All updates have to first go through the server. The server determines the latest document revision and holds the source of truth.
Robustness: When new participants join or one of the existing clients crash (due to bugs, network flakiness, etc), the latest document can be fetched from the server.

Disadvantages:
Single point of failure: The central server is a critical component; if it fails, the entire network can be disrupted.
Cost: Higher infrastructure and maintenance costs due to the need for powerful central servers.
Scalability: Can become a bottleneck if the number of clients grows rapidly without proper scaling.

Concurrency control model:
2 kinds of updates:
1. local update by user
2. merge update by peer

We need concurrency control to ensure we avoid conflicts eg editing the same sentence by 2 users.
We need to have a local replica of the ui doc so that user's change would appear instantly
We can use version-detection model.
In a version-detection model, the document state is replicated in each user's machine and participants can make changes locally,
which are then propagated to peers as soon as possible. Under good network connections, users should see updates from peers in 
under a second.
Each update request contains the new data and the document revision the change was acted on. When the server receives the update 
request, it first checks if the revision in the request is the same as the current revision. If the revisions match, the server 
updates the document, saves it as a new revision, and broadcasts this information to all peers so that everyone is on the latest 
revision. If they are different, then there's a "version mismatch" which can be resolved by:
 we can use conflict resolution methods like Operational Transformations (OTs). On the other hand, 
 if Conflict-free Replicated Data Types (CRDTs) are used, there is no need for compensation.

Only the version-detection consistency model is able to meet all the real-time collaborative editing requirements because it has the following properties:
Replicated: The document is replicated in the machines of all participants. This is necessary for the model to make optimistic updates.
Optimistic and non-blocking: Updates are made locally, without worrying about conflicts. Optimistic behavior is necessary for zero-latency responsiveness during local updates – the speed or reliability of your network connection will not influence how fast users can type.
No locking: The entire document is available to every participant all the time.
Automatic conflict resolution: Any detected conflicts are resolved automatically on the server. Possible approaches include creating compensating changes and informing the client (OT), or using data structures that resolve conflicts automatically (CRDTs).
From each participant's perspective, it will feel as if they are editing an offline Word document – there is no latency involved when editing.

Two common conflict resolution approaches are used:
Operational Transformations (OT): OT accounts for context at the point of editing and transforms the operations accordingly (e.g. by modifying the offsets of insertions/deletions).
Conflict-free Replicated Data Types (CRDTs): CRDTs enforce the use of data structures where updates are commutative and associative such that the order of operations does not matter.

### **R - Requirements**

**Functional Requirements:**

1.  **Document CRUD:** Users can create, read, update, and delete documents.
2.  **Real-Time Collaboration:** Multiple users can edit the same document simultaneously, seeing each other's cursors and changes instantly.
3.  **Version History:** The system must maintain a complete history of revisions, allowing users to view or revert to previous states.

**Non-Functional Requirements:**

1.  **Low Latency:** Crucial for a smooth editing experience. Typing must feel instantaneous.
2.  **High Consistency:** All concurrent users must eventually see the exact same document state.
3.  **High Availability & Reliability:** No data loss; service must always be accessible.
4.  **Scalability:** Must support millions of daily active users and thousands of concurrent edits on hot documents.

-----

### **A - Architecture (High-Level)**

The architecture relies on a central server acting as the source of truth to manage synchronization over persistent connections.

  * **Client:** Single-page application holding a local copy of the document state. It handles capturing user edits and rendering incoming changes.
  * **Load Balancer / API Gateway:** Routes HTTP requests for metadata and upgrades connections to WebSockets for editing sessions.
  * **Collaboration Service (WebSocket Server):** The core component. It maintains persistent WebSocket connections with active clients, receives operations, performs Operational Transformation (OT), and broadcasts changes.
  * **Document Service:** A standard REST service managing document metadata (titles, permissions, folder structure).
  * **Redis (Hot Storage):** Acts as a high-speed temporary store for the current document state and active user sessions to ensure low latency during active editing.
  * **Database Cluster (Cold Storage):**
      * **SQL DB (e.g., PostgreSQL):** Stores structured metadata (User info, Document permissions).
      * **NoSQL/Append-Only DB (e.g., Cassandra or MongoDB):** Stores the immutable log of all *operations* (the revision history).

-----

### **D - Data Model**

A core concept is that a document is not stored as a large blob of text, but rather as an ordered sequence of **operations**.

**1. Operations Log (Immutable History)**
This is the source of truth. Every keystroke or formatting change is an entry.

```json
{
  "doc_id": "doc_123",
  "revision_id": 105,
  "user_id": "user_A",
  "timestamp": 1678886400,
  "op_data": {
    "type": "insert",
    "position": 45,
    "content": "hello world",
    "attributes": { "bold": true }
  }
}
```

**2. Document Snapshot**
To speed up loading, the full state of a document is cached periodically (e.g., every 100 revisions).

```json
{
  "doc_id": "doc_123",
  "snapshot_revision_id": 100,
  "content_state": { ...full document structure... }
}
```

*Loading a Doc = Fetch latest Snapshot + Replay operations since that snapshot.*

**3. Metadata (SQL)**
Standard relational tables for `Users`, `Documents` (title, owner), and `Permissions` (editor/viewer access).

-----

### **I - Interfaces (API)**

The system uses a hybrid approach: REST for metadata and WebSockets for core editing.

**REST API (Metadata & Setup)**

  * `POST /api/docs` -\> Create a new document.
  * `GET /api/docs/{docId}` -\> Fetch document metadata and initial state info (e.g., latest revision number to connect with).

**WebSocket API (Real-Time Collaboration)**
Once connected, communication is bi-directional via JSON payloads.

  * **Client sends operation:**
    ```json
    { "type": "op", "docId": "d1", "rev": 10, "op": {"insert": "x", "pos": 5} }
    ```
  * **Server acknowledges (after transforming):**
    ```json
    { "type": "ack", "rev": 11 }
    ```
  * **Server broadcasts changes to others:**
    ```json
    { "type": "new_op", "user": "Bob", "op": {...transformed op...} }
    ```

### **O - Optimizations & Deep Dives**

The critical challenge is handling concurrent edits without conflicts.

**1. Operational Transformation (OT)**
This is the chosen mechanism for conflict resolution (preferred over CRDTs for central-server models like Google Docs).

  * **The Problem:** User A inserts "A" at index 0. User B simultaneously inserts "B" at index 0. Without OT, the final state diverges based on arrival order.
  * **The Solution:** The server acts as the final judge. When it receives an operation defined against an older revision, it "transforms" that operation against all intervening operations that have happened since.
  * **Client Logic:** Clients must maintain complex states to handle their own pending changes versus incoming transformed changes from the server (often categorized as *Synchronized, Awaiting Confirmation, Awaiting With Buffer*).

**2. Efficient Bandwidth Usage**
Only send **deltas** (small operation objects), never the full document text, over the WebSocket connection.

**3. Snapshotting Strategy**
As mentioned in the Data Model, reconstructing a document with 50,000 revisions by replaying them one by one is too slow. The system periodically saves the flattened state to object storage. Loading a document becomes an O(K) operation, where K is the number of revisions since the last snapshot.
